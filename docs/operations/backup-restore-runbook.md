# 데이터베이스·미디어 백업 및 복구 런북

## 목표와 범위

운영 목표는 우선 `RPO 15분`, `RTO 4시간`으로 두고 실제 Supabase 플랜·Storage 복제 방식이 이를 만족하는지 출시 전에 확인한다. 범위에는 Postgres, Auth 연계 데이터, 비공개 Storage 객체, 버킷 설정, Edge Function/서버 설정, 마이그레이션과 복구용 메타데이터가 포함된다.

중요: Supabase 데이터베이스 백업은 Storage 객체 자체를 복원하지 않는다. DB와 객체를 같은 복구 지점으로 묶지 않으면 게시글·채팅에 경로만 남고 사진·영상은 사라질 수 있다.

## 백업 정책

| 자산 | 방식 | 보존 | 검증 |
| --- | --- | --- | --- |
| Postgres | 플랜의 PITR 또는 일일 논리 백업과 암호화된 별도 계정 저장소 | 일일 35일, 월간 12개월 제안 | 매일 완료·크기·체크섬 확인 |
| Storage | 객체 inventory와 변경분 복제, 가능하면 버전 관리되는 다른 공급자/계정 | 삭제 유예 35일 이상 | 객체 수·바이트·해시 대조 |
| 설정 | `supabase/`, RLS, 함수, 버킷 정책, 배포 설정을 Git으로 버전 관리 | 영구 | CI 재구축 시험 |
| 키·비밀 | 관리형 secret store와 별도 복구 절차 | 현재값+회전 이력 | 분기별 접근·회전 시험 |

백업 작업은 전용 최소권한 runner에서만 service-role/DB 자격증명을 사용한다. 로그에 JWT, DB URL, 사용자 이메일, 파일 경로의 민감한 부분을 남기지 않는다. 백업은 전송·저장 암호화하고 운영 계정 침해가 백업 삭제로 이어지지 않도록 별도 계정과 변경 불가 보존을 사용한다.

## 장애 시 복구 절차

1. 사고 시각과 마지막 정상 시각을 기록하고 쓰기 중지 또는 점검 모드를 선언한다.
2. 삭제·오염·계정 침해 범위를 판단하고 자격증명을 회전한다. 원본을 덮어쓰지 않는다.
3. 격리된 새 프로젝트에 마이그레이션 버전과 확장, Auth/Storage 설정을 먼저 준비한다.
4. 목표 복구 시점의 DB를 복원하고 행 수, FK, RLS, RPC 실행 권한, audit 연속성을 확인한다.
5. 같은 cutoff의 Storage inventory를 기준으로 객체를 복원하고 크기·해시·DB 참조를 대조한다.
6. 고아 객체와 누락 참조를 보고서로 만들고 자동 삭제하지 않는다.
7. 테스트 계정으로 로그인, 가입·승인, 게시·미디어 조회, 채팅, 임원 권한을 smoke test한다.
8. 보안·제품 책임자가 승인한 뒤 DNS/환경변수 전환 또는 기존 프로젝트 복구를 수행한다.
9. 사용자 통지, 데이터 손실 범위, 실제 RPO/RTO와 후속 조치를 기록한다.

## 분기별 복구 훈련

- 운영과 분리된 임시 프로젝트를 사용하고 실제 수신자에게 이메일·푸시가 발송되지 않게 한다.
- 임의의 DB 시점과 Storage inventory를 선택해 전체 복구한다.
- 최근 게시물·채팅 미디어 100개 이상을 표본 해시 검증한다.
- RLS 공격 테스트와 pgTAP을 실행한다.
- 목표 RPO/RTO, 담당자 호출시간, 누락 단계, 비용을 기록한다.
- 훈련 프로젝트와 임시 자격증명은 검증 후 승인된 절차로 폐기한다.

백업 성공 알림만으로 복구 가능성을 판단하지 않는다. 분기별 복구 증거가 없으면 출시 상태는 `HOLD`다.
